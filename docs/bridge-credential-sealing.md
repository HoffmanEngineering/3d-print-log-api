# Sealing LAN credentials to a bridge (`printlog-credential` v1)

A printer's LAN credential (a Bambu Lab access code, a PrusaLink password, a Moonraker API key) is
encrypted in the browser to the public key of the printlog-bridge that will use it. The API stores
and forwards only the ciphertext and cannot read it. Only the bridge, which holds the private key,
can. This is printlog-bridge#100, "LAN credentials": story 14a (this scheme and the API), 14b (the
bridge), 14c (the web app).

Three implementations must agree byte for byte, so every parameter is pinned here. **MUST**,
**MUST NOT** and **SHOULD** are normative.

- The bridge: Python 3.9+, with the [`cryptography`](https://cryptography.io) package.
- The browser: WebCrypto only (`crypto.subtle`), no JavaScript crypto library.
- The API: .NET 10. It never decrypts. It parses the bridge's public key strictly and checks the
  shape of each sealed value. The test project carries a reference sealer and opener.

Files next to this one:

- `bridge-credential-sealing.vectors.json`: copy it into the bridge and web app test suites. It has:
  - a test keypair;
  - seven vectors with every intermediate value, three of them with a `typed` input showing the
    trimming and normalization rules;
  - eleven ciphertexts that must not open, each with a `reason`: `authentication` (fails the tag:
    report `undecryptable`) or `plaintext` (opens, but isn't a credential: report
    `invalid_plaintext`);
  - invalid public keys and invalid sealed values.
- `bridge-credential-sealing.check.py` and `bridge-credential-sealing.check.mjs`: reference
  implementations in Python (`cryptography`) and WebCrypto (Node 20+ or a browser). Each one:
  - opens every vector and reseals it byte for byte from its fixed ephemeral key and nonce;
  - applies `prepare` to each `typed` input;
  - round-trips a fresh seal;
  - fails every `mustNotOpen` entry the way its `reason` says.

  Run them with the vectors file as the argument. `BridgeCredentialSealingTests` does the same in
  .NET on every CI run.

## The construction

An ECIES-style sealed box: an ephemeral ECDH key agreement on P-256, HKDF-SHA256, AES-256-GCM.

**Why P-256 and not X25519.** Every browser has had ECDH P-256 in WebCrypto for years. X25519
only landed in Chrome 133, Firefox 130 and Safari 17 (the Android WebView follows Chrome), so a
user on an older Safari or a pinned WebView could not seal. Python's `cryptography` and .NET
support both. P-256 costs a slightly larger key (65 bytes raw) and nothing else that matters here.
AES-GCM rather than ChaCha20-Poly1305 for the same reason: WebCrypto has no ChaCha20.

**Why the bridge needs one dependency.** The Python standard library has no elliptic curves.
`cryptography` is the one well-maintained choice. It ships wheels for linux x86_64 and aarch64, and
Debian (`python3-cryptography`) and Alpine (`py3-cryptography`, the Home Assistant base) package it
for armv7. The bridge should import it lazily. A bridge without it still runs printers from its
config file, and reports that app credentials need the package.

### Keys

- **The bridge's key**: one P-256 keypair, generated by the bridge (at pairing, or on first start
  without one) and kept in its state directory, readable only by the bridge's user (mode 0600). It
  never leaves the bridge: not in a check-in, a log, `status`, `doctor` or a support bundle.
  Suggested file: `<state_dir>/credential-key.pem`, PKCS#8 PEM, unencrypted. The bridge SHOULD keep
  its key across re-pairing and upgrades. A new key forces the owner to confirm it and to enter
  every credential again (below).
- **The public key on the wire**: the DER `SubjectPublicKeyInfo` (SPKI) with an **uncompressed**
  point, in standard base64 **with** padding.
  - It is always exactly 91 bytes, so always exactly 124 characters, always starting
    `MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE`.
  - WebCrypto: `exportKey('spki', …)` / `importKey('spki', …)`. Python: `public_bytes(Encoding.DER,
    PublicFormat.SubjectPublicKeyInfo)`.
  - The API drops anything else (another curve, a compressed point, PEM, base64url, missing
    padding, whitespace, trailing bytes, a point off the curve).
- **The fingerprint**: lower-case hex of SHA-256 over those 91 SPKI bytes, 64 characters.
  - Where a person compares fingerprints, show the first 16 characters in groups of four
    (`aed0 3e9a 8282 33b2` for the test key): the web app next to the bridge, and the bridge in
    `status` and on its local page.
  - **Whoever seals MUST compute the fingerprint itself, over the exact SPKI bytes it imported and
    sealed to.** It shows that fingerprint to the user and sends that fingerprint to the API.
  - **The sealer MUST NOT display or send back the API's `publicKeyFingerprint` or
    `pendingPublicKeyFingerprint`.** Those fields are a convenience for listing and logs. A
    malicious API could return its own key alongside the real bridge's fingerprint, and a
    fingerprint the browser copied from the API would hide the swap.

### What may be sealed

These rules are the same for every implementation. The vectors cover each one.

- **Plaintext** is 1 to 256 bytes of UTF-8 with **no control characters**:
  - not U+0000–U+001F (C0, including tab and line feed);
  - not U+007F (delete);
  - not U+0080–U+009F (C1).

  C1 is refused too: no printer credential contains one, they render invisibly, and some
  terminals and log viewers act on them.
- **Trimming, by field.** The sender removes U+0020 (space) and U+00A0 (no-break space) from both
  ends of `access_code`, `username`, `api_key` and `moonraker_api_key`. These are copied from a
  printer's screen or a web page, where a stray space is common and never meaningful. **A
  `password` is never trimmed**: a space at either end may be part of it.
- **No Unicode normalization** (no NFC, no NFKC). The sender seals the code points as typed. The
  printer compares what it stored with what it receives, so normalizing could turn a working
  password into one the printer refuses. Vector 7 seals the NFD spelling of `café`
  (`63 61 66 65 cc 81`) as is.
- The sender checks all of this before sealing (the API can't). The bridge checks it again after
  opening, and then uses the value **exactly as opened**: no trimming, no normalization.

### Sealing one value (the browser)

Inputs: the bridge's SPKI public key `R`, the bridge id `B` and desired-printer entry id `E`
(decimal integers, as the API returns them), the field name `F` (below), and the plaintext `P`
after the rules above.

1. Compute the fingerprint of `R`'s bytes (above). This is the fingerprint you show and send.
2. Generate a fresh ephemeral P-256 keypair `e` **for every value sealed**. Never reuse one.
3. `shared` = ECDH(`e.private`, `R`): the 32-byte x-coordinate.
   - WebCrypto: `deriveBits({name: 'ECDH', public: R}, e.privateKey, 256)`.
   - Python: `private_key.exchange(ec.ECDH(), public_key)`.
   - .NET: `DeriveRawSecretAgreement`.
4. `ephRaw` = `e.public` as an uncompressed point (65 bytes, `0x04 ‖ X ‖ Y`; WebCrypto
   `exportKey('raw', …)`). `recipientRaw` = `R` as an uncompressed point (65 bytes).
5. `key` = HKDF-SHA256 with:
   - IKM = `shared`;
   - salt = `ephRaw ‖ recipientRaw` (130 bytes);
   - info = ASCII `printlog-credential:v1:aes-256-gcm`;
   - length = 32 bytes.
6. `nonce` = 12 random bytes. (The key is already unique per message. A random nonce costs nothing
   and survives a bug that reuses an ephemeral key.)
7. `ad` = ASCII `printlog-credential:v1:{B}:{E}:{F}`, e.g. `printlog-credential:v1:42:7:access_code`.
   No padding or leading zeros on the numbers.
8. `ct ‖ tag` = AES-256-GCM-Encrypt(`key`, `nonce`, `P`, additional data = `ad`), with a 16-byte
   tag. WebCrypto's default `tagLength: 128` appends it, as does Python's `AESGCM.encrypt`.
9. The sealed value is the ASCII string `v1.` followed by base64url **without padding** of
   `ephRaw (65) ‖ nonce (12) ‖ ct (len P) ‖ tag (16)`.

So a sealed value is 94 to 349 bytes before encoding, and 129 to 469 characters.

### Opening one value (the bridge)

1. **Check the shape.** Refuse unless all of these hold:
   - the value matches `^v1\.[A-Za-z0-9_-]+$`;
   - it decodes (canonical base64url, no padding) to 94 to 349 bytes;
   - the first byte is `0x04`.

   An unknown version prefix means a newer app sealed this: report it as `undecryptable`, don't
   guess.
2. **Split** `ephRaw` (bytes 0–64), `nonce` (65–76), and `ct ‖ tag` (77–end). Load `ephRaw` as a
   P-256 point, and refuse it if it isn't on the curve (`EllipticCurvePublicKey.from_encoded_point`
   raises).
3. **Decrypt.** Recompute `shared`, `key` and `ad` from **its own** bridge id, the entry id and the
   field it is reading (never from anything inside the value), then AES-GCM-decrypt. Any of these
   fails the tag (`InvalidTag`): a wrong key, a value moved to another bridge, entry or field, or
   any changed bit. Report it as `undecryptable`.
4. **Check the plaintext.** Decode it as strict UTF-8 and apply the rules in "What may be sealed".
   Invalid UTF-8, a control character, or a length outside 1–256 bytes: report `invalid_plaintext`
   and don't use it.
5. **Use it.** Keep the plaintext in memory only, or, if the bridge persists it, in its state
   directory with the key's permissions. Never log it. If the printer refuses it, report
   `rejected_by_printer`.

### What binds a value to its place

The associated data names the bridge, the desired-printer entry and the field, so the API (or
anyone with database access) cannot move a ciphertext. An access code sealed for entry 7 does not
open as entry 8's, as a password, or on another bridge. The salt carries both public keys, so a
value sealed to one key never opens under another. The API deletes sealed values with their entry,
and entry ids are SQL Server identity values that are not reused.

## Key changes and the version prefix

- `v1.` versions the whole construction. A future `v2.` changes the prefix, the HKDF info and the
  `v1` in the associated data, so the versions cannot be confused. The API accepts only `v1.` today.
- **The first key a bridge reports is taken as is** (trust on first use, right after the owner
  paired it).
- **A different key later is held pending** until the owner confirms it:
  - The bridge might have regenerated its key, or a stolen device token might be reporting its own.
  - The current key stays in use, so nothing goes stale and the bridge keeps the values it can
    open.
  - The API refuses seals to the pending key (409 `bridge_key_unconfirmed`), creates an in-app
    notification ("<bridge> reported a new encryption key; confirm it on the Bridges screen"), and
    shows the pending key on the bridge.
- **Confirming.** The owner compares the pending key's fingerprint, computed by the web app from
  `pendingPublicKey`, with the one the bridge shows. The web app then confirms it, sending that
  fingerprint. On confirmation:
  - it becomes the current key;
  - every value sealed to the old key becomes **stale**: kept and marked, no longer sent to the
    bridge;
  - the desired version changes;
  - the web app asks for those credentials again.
- **Further reports.** A later report of the current key leaves the pending one alone. Another new
  key replaces it (and notifies again). There is no "reject": a pending key nobody confirms is
  harmless, and if the owner suspects the device, revoking it is the remedy.
- **Re-pairing** the same bridge (the same device id) keeps the same bridge id and its key if the
  bridge keeps it. Revoking the device deletes the bridge, its desired printers and their sealed
  values.

## Trust model

- **Confidentiality from the cloud.** The API, its database and its backups hold only ciphertext.
  - Logs, telemetry, the sync snapshot, MCP and webhooks never carry sealed values.
  - The owner's own endpoints don't return them either: the browser can't open them, so it gets
    field names, fingerprints and times.
  - Only the bridge's own device endpoints return them.
- **Not integrity from the cloud.** The public key is public, so anyone holding it, the API
  included, can seal a value the bridge will accept.
- **Key substitution by the API.** A malicious API could hand the browser its own key in place of
  the bridge's, and read what the user seals. The defense is the fingerprint:
  - the web app computes it from the key it actually seals to (never trusting the API's copy);
  - the bridge shows its own;
  - a user who compares them detects the swap.
- **A stolen device token** can report a new key, but it is held pending: nothing is sealed to it
  until the owner confirms it, and confirming means comparing fingerprints with the real bridge.
  - Key changes are counted per bridge per UTC day (`BridgeKeyChanged` telemetry,
    `ChangesToday`), so a bridge whose key flips shows up.
  - Revoking the device ends it.
- **Lengths are visible.** The ciphertext is as long as the plaintext: an 8-digit access code looks
  like one. Not padded, because the fields are short and their formats are public anyway.

## Fields

| Kind | Fields |
|---|---|
| `bambu` | `access_code` |
| `prusalink` | `password`, `username`, `api_key` |
| `moonraker` | `moonraker_api_key` |
| `octoprint` | `api_key` |
| `sdcp` | none |

These are printlog-bridge's adapters' `app_secrets`, the same names as the interim
`[app_printer <id>]` section. `username` is not secret, but sealing it keeps one mechanism. The API
refuses a field the entry's kind doesn't take, and lists each entry's fields as `secretFields`.

## Checklists

**The web app (14c) MUST:**

- [ ] Seal with WebCrypto exactly as above, to the `publicKey` from `GET /api/bridges/{id}`.
- [ ] Compute the fingerprint itself from the SPKI bytes it sealed to (or is about to confirm), show
      that, and send that as `keyFingerprint` / `fingerprint`. Never display or echo the API's
      `publicKeyFingerprint` or `pendingPublicKeyFingerprint`.
- [ ] Apply the plaintext rules: trim per field, no normalization, refuse control characters and
      anything over 256 bytes, with a message, before sealing.
- [ ] When the bridge has a `pendingPublicKey`, show "this bridge reported a new encryption key on
      …", both fingerprints (computed), and ask the user to compare with the bridge's `status` or
      local page before confirming.
- [ ] Check `stale` on every secret in the `PUT …/secrets/{field}` 200 response. A seal that raced a
      key confirmation is stored but stale: ask again.
- [ ] Handle `bridge_key_changed` and `bridge_key_unconfirmed` by reloading the bridge, never by
      retrying with a fingerprint from the response.
- [ ] Never store the plaintext. Run the vectors (fixed ephemeral JWK and nonce must give `sealed`;
      every `typed` must `prepare` to `plaintext`).

**The bridge (14b) MUST:**

- [ ] Generate and keep one P-256 key (0600), and show its fingerprint (first 16 hex, grouped) in
      `status`, `doctor` and the local page, saying when the app hasn't confirmed it yet
      (`pendingPublicKeyFingerprint` in the check-in response equals yours).
- [ ] Send `publicKey` on every check-in.
- [ ] Open as above: shape check, curve check, AD from its own ids, strict UTF-8 and control
      characters after opening; use the value exactly as opened.
- [ ] Send `credentialIssues` (with `credentialIssuesVersion`) on **every** check-in once it has
      applied a desired version: `[]` when everything works.
- [ ] Never log a plaintext, a sealed value or the private key. Run the vectors, including every
      `mustNotOpen` with its `reason`.

## The API contract

### Check-in (`PUT /api/bridges/me`, the bridge)

New optional fields:

```json
{
  "publicKey": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAEvzmvDhTjuEWPAzuAqS3zfIP6QeXk2aXjK7BFOitKjtD4GHy/T1GLRiXStoJ7gGOhQAlWoMuHkeYLw0k/VVhsTQ==",
  "publicKeyFingerprint": "aed03e9a828233b23fcecb8c927642f3f9dda453f3016d8314abfce62e64b38c",
  "credentialIssuesVersion": "3f2b9c0e8d7a4b6c9e1f2a3b4c5d6e7f",
  "credentialIssues": [
    { "entryId": 7, "field": "access_code", "code": "undecryptable" }
  ]
}
```

- **`publicKey`**: send it on every check-in. Missing or null keeps what is stored.
  - A key that isn't exactly the shape above, or a `publicKeyFingerprint` that doesn't match it, is
    dropped. It is named in `rejected` (`publicKey` or `publicKeyFingerprint`, code
    `invalid_public_key`), the stored key stays, and the rest of the check-in is stored.
  - The first key is taken. A different one later is held pending (above).
- **`credentialIssues`**: what the bridge can't use, at most 200.
  - Send it on **every** check-in once you have applied a desired version, as the complete list
    (`[]` when everything works). It replaces the stored issues of all your entries. A missing or
    null field keeps the stored issues; that is only for bridges that predate this.
  - Codes:
    - `missing`: the adapter needs this field and has no value it can open. This includes a value
      sealed to an old key, which isn't sent.
    - `undecryptable`: a value is there and fails its tag, or has an unknown version.
    - `invalid_plaintext`: it opened, but it is not valid UTF-8, has a control character, or is the
      wrong length.
    - `rejected_by_printer`: it opened and passed, and the printer refused it.
  - An entry that isn't on this bridge, a field its kind doesn't take, or another code is dropped
    and named in `rejected` (`unknown_printer_entry`, `invalid_secret_field`, `invalid_issue_code`).
- **`credentialIssuesVersion`**: the desired `version` the issues describe, required with
  `credentialIssues`.
  - The issues are applied only when it equals the current version. A report about a value the
    user has since replaced never lands on the new one; it is ignored, and the next check-in
    reports again.
  - The write is also conditional on the entry not having changed since it was read, so a seal
    that lands in the middle of a check-in keeps the issue it cleared.
  - `credentialIssues` without a version, or over 200, is a 400 `invalid_check_in`.
- **The response** adds:
  - `publicKeyFingerprint`: the key values are sealed to, or null before the first one;
  - `pendingPublicKeyFingerprint`: a newer key of yours waiting for the owner's confirmation, or
    null.

### The desired list (check-in response and `GET /api/bridges/me/desired`, the bridge)

Each printer gains:

```json
{
  "id": 7,
  "kind": "bambu",
  "secretFields": ["access_code"],
  "secrets": [
    {
      "field": "access_code",
      "sealed": "v1.BJG56n7OnSEn_CzrpjZkPC3AFR-jTiDAgEcFyGZxh6N7Zbe…",
      "keyFingerprint": "aed03e9a828233b23fcecb8c927642f3f9dda453f3016d8314abfce62e64b38c",
      "updatedAt": "2026-10-27T18:05:00+00:00",
      "stale": false
    }
  ],
  "credentialIssues": []
}
```

- Only values sealed to the bridge's current key are listed.
- Setting, replacing or clearing one changes `version`, and so does confirming a new key.
- The bridge opens each value with `printlog-credential:v1:{bridgeId}:{id}:{field}`. `bridgeId` is
  in the check-in response.
- A value that is absent where the adapter needs one is `missing`.
- Values from the interim `[app_printer <id>]` section may stay as a local override.

### Owner endpoints (the web app; `InteractiveUserOnly`)

- **`BridgeDto`** adds:
  - `publicKey`, `publicKeyFingerprint`, `publicKeyChangedAt`. These are null until the bridge
    sends a key: an older bridge can't take sealed credentials, so say "update the bridge".
  - `pendingPublicKey`, `pendingPublicKeyFingerprint`, `pendingPublicKeyAt`.
  - Both fingerprints are convenience only (see the checklist).
- **`BridgePrinterDto`** (in `GET /api/bridges/{id}/printers` and the connect response) adds:
  - `secretFields`;
  - `secrets`: each `field`, `keyFingerprint`, `updatedAt` and `stale`, **never** `sealed`;
  - `credentialIssues`: each `field` and `code`.
- **`PUT /api/bridges/{id}/printers/{entryId}/secrets/{field}`** with
  `{ "sealed": "v1.…", "keyFingerprint": "<the fingerprint you computed and sealed to>" }`:
  - sets or replaces one value and returns the entry (200, `BridgePrinterDto`);
  - clears that field's issue and changes the desired version;
  - check `stale` in the response.
- **`DELETE /api/bridges/{id}/printers/{entryId}/secrets/{field}`** clears one value (204, also when
  there was none). It changes the desired version if there was a value.
- **`POST /api/bridges/{id}/public-key/confirm`** with `{ "fingerprint": "<computed from
  pendingPublicKey>" }` makes the pending key current. It returns the bridge (200, `BridgeDto`).
- **Errors** are problem details with a `code`.
  - 404: a bridge or entry that isn't yours.
  - 400:
    - `invalid_secret_field`: not one of the entry's `secretFields`;
    - `invalid_sealed_value`: not the shape above. The API checks the prefix, the encoding, the
      length and that the ephemeral key is on the curve, and nothing else;
    - `invalid_key_fingerprint`: not 64 lower-case hex characters.
  - 409:
    - `bridge_key_missing`: the bridge has reported no key yet;
    - `bridge_key_unconfirmed`: sealed to the pending key; confirm it first;
    - `bridge_key_changed`: the fingerprint isn't the bridge's current one; reload the bridge,
      compare, and seal again;
    - `no_pending_key`: confirm, with nothing pending;
    - `pending_key_changed`: confirm, but the bridge reported another key since you loaded it;
      reload and compare again.
