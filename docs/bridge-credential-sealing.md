# Sealing LAN credentials to a bridge (`printlog-credential` v1)

A printer's LAN credential (a Bambu Lab access code, a PrusaLink password, a Moonraker API key) is
encrypted in the browser to the public key of the printlog-bridge that will use it. The API stores
and forwards only the ciphertext and cannot read it. Only the bridge, which holds the private key,
can. This is printlog-bridge#100, "LAN credentials": story 14a (this scheme and the API), 14b (the
bridge), 14c (the web app).

Three implementations must agree byte for byte, so every parameter is pinned here:

- the bridge, Python 3.9+, with the [`cryptography`](https://cryptography.io) package;
- the browser, WebCrypto only (`crypto.subtle`), no JavaScript crypto library;
- the API, .NET 10, which never decrypts: it parses the bridge's public key strictly and checks the
  shape of each sealed value. The test project carries a reference sealer and opener.

Files next to this one:

- `bridge-credential-sealing.vectors.json`: a test keypair, four vectors with every intermediate
  value, five ciphertexts that must not open, and invalid public keys and sealed values. Copy it
  into the bridge and web app test suites.
- `bridge-credential-sealing.check.py` and `bridge-credential-sealing.check.mjs`: reference
  implementations in Python (`cryptography`) and WebCrypto (Node 20+ or a browser) that open every
  vector, reseal it byte for byte from its fixed ephemeral key and nonce, round-trip a fresh seal,
  and refuse every `mustNotOpen` entry. Run them with the vectors file as the argument.
  `BridgeCredentialSealingTests` does the same in .NET on every CI run.

## The construction

An ECIES-style sealed box: an ephemeral ECDH key agreement on P-256, HKDF-SHA256, AES-256-GCM.

**Why P-256 and not X25519.** WebCrypto has had ECDH P-256 in every browser for years; X25519 only
landed in Chrome 133, Firefox 130 and Safari 17 (and the Android WebView follows Chrome), so a
user on an older Safari or a pinned WebView could not seal. Python's `cryptography` and .NET do
both. P-256 costs a slightly larger key (65 bytes raw) and nothing else that matters here. AES-GCM
over ChaCha20-Poly1305 for the same reason: WebCrypto has no ChaCha20.

**Why the bridge needs one dependency.** The Python standard library has no elliptic curves.
`cryptography` is the one well-maintained choice; it ships wheels for linux x86_64 and aarch64, and
Debian (`python3-cryptography`) and Alpine (`py3-cryptography`, the Home Assistant base) package it
for armv7. The bridge should import it lazily, so a bridge without it still runs printers from its
config file and reports that app credentials need it.

### Keys

- **The bridge's key**: one P-256 keypair, generated by the bridge (at pairing or on first start
  without one) and kept in its state directory, readable only by the bridge's user (mode 0600). It
  never leaves the bridge: not in a check-in, a log, `status`, `doctor` or a support bundle.
  Suggested file: `<state_dir>/credential-key.pem`, PKCS#8 PEM, unencrypted.
- **The public key on the wire**: the DER `SubjectPublicKeyInfo` (SPKI) with an **uncompressed**
  point, in standard base64 **with** padding: always exactly 91 bytes, so always exactly 124
  characters, and always starting `MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE`. WebCrypto:
  `exportKey('spki', …)` / `importKey('spki', …)`. Python: `public_bytes(Encoding.DER,
  PublicFormat.SubjectPublicKeyInfo)`. The API refuses anything else (another curve, a compressed
  point, PEM, base64url, missing padding, whitespace, trailing bytes, a point off the curve).
- **The fingerprint**: lower-case hex of SHA-256 over those 91 SPKI bytes, 64 characters. The API
  computes it; the bridge may send it too and the API checks they agree. Show the first 16
  characters in groups of four (`6912 dab0 8362 8b44`) where a person compares them: the web app
  next to the bridge, the bridge in `status` and on its local page.

### Sealing one value (the browser)

Inputs: the bridge's SPKI public key `R`, the bridge id `B` and desired-printer entry id `E`
(decimal integers, as the API returns them), the field name `F` (below), and the plaintext `P`.

1. `P` is the credential as UTF-8, 1 to 256 bytes, with no control characters (U+0000–U+001F,
   U+007F). Trim what the user typed only where the field allows it (an access code: yes; a
   password: no). The sender checks this; the API cannot.
2. Generate a fresh ephemeral P-256 keypair `e` **for every value sealed**. Never reuse one.
3. `shared` = ECDH(`e.private`, `R`): the 32-byte x-coordinate. WebCrypto: `deriveBits({name:
   'ECDH', public: R}, e.privateKey, 256)`. Python: `private_key.exchange(ec.ECDH(), public_key)`.
   .NET: `DeriveRawSecretAgreement`.
4. `ephRaw` = `e.public` as an uncompressed point (65 bytes, `0x04 ‖ X ‖ Y`; WebCrypto
   `exportKey('raw', …)`). `recipientRaw` = `R` as an uncompressed point (65 bytes).
5. `key` = HKDF-SHA256(IKM = `shared`, salt = `ephRaw ‖ recipientRaw` (130 bytes),
   info = ASCII `printlog-credential:v1:aes-256-gcm`, length = 32 bytes).
6. `nonce` = 12 random bytes. (The key is already unique per message; a random nonce costs nothing
   and survives a bug that reuses an ephemeral key.)
7. `ad` = ASCII `printlog-credential:v1:{B}:{E}:{F}`, e.g. `printlog-credential:v1:42:7:access_code`.
   No padding or leading zeros on the numbers.
8. `ct ‖ tag` = AES-256-GCM-Encrypt(`key`, `nonce`, `P`, additional data = `ad`), with a 16-byte tag
   (WebCrypto's default `tagLength: 128` appends it, as does Python's `AESGCM.encrypt`).
9. The sealed value is the ASCII string `v1.` followed by base64url **without padding** of
   `ephRaw (65) ‖ nonce (12) ‖ ct (len P) ‖ tag (16)`.

So a sealed value is 94 to 349 bytes before encoding, and 129 to 469 characters.

### Opening one value (the bridge)

1. Refuse unless the value matches `^v1\.[A-Za-z0-9_-]+$`, decodes (base64url, no padding) to 94
   to 349 bytes, and the first byte is `0x04`. An unknown version prefix means "a newer app sealed
   this": report it (below), don't guess.
2. Split `ephRaw` (bytes 0–64), `nonce` (65–76), and `ct ‖ tag` (77–end). Load `ephRaw` as a P-256
   point; refuse if it isn't on the curve (`EllipticCurvePublicKey.from_encoded_point` raises).
3. Recompute `shared`, `key` and `ad` from **its own** bridge id, the entry id and the field it is
   reading (never from anything inside the value), and AES-GCM-decrypt. A wrong key, a value moved
   to another bridge, entry or field, or any changed bit fails the tag (`InvalidTag`).
4. Decode UTF-8 strictly and refuse control characters.
5. Keep the plaintext in memory only (or, if the bridge persists it, in its state directory with the
   key's permissions). Never log it.

### What binds a value to its place

The associated data names the bridge, the desired-printer entry and the field, so the API (or
anyone with database access) cannot move a ciphertext: an access code sealed for entry 7 does not
open as entry 8's, as a password, or on another bridge. The salt carries both public keys, so a
value sealed to one key never opens under another. Entry ids are never reused (identity columns),
so a value cannot outlive its printer onto a new one.

## Rotation and the version prefix

- `v1.` versions the whole construction. A future `v2.` changes the prefix, the HKDF info and the
  associated data's `v1`, so the versions cannot be confused. The API accepts only `v1.` today.
- **The bridge's key changes** when it regenerates it (its state directory was lost, or it rotates
  on purpose). The API cannot read the old values, so it cannot move them to the new key: every
  value sealed to the old key becomes **stale**. The bridge reports the new key in its next
  check-in; the API stores it, bumps the desired version, stops sending the stale values to the
  bridge, and marks them `stale` in the owner's views. The web app asks for those credentials
  again. Stale values are kept, not deleted, so the owner sees which fields need re-entering, and a
  bridge restored from a backup with its old key reads them again.
- **Re-pairing** the same bridge (the same device id) keeps the same bridge id, and its key if the
  bridge keeps it. Revoking the device deletes the bridge, its desired printers and their sealed
  values.

## Trust model

- **Confidentiality from the cloud.** The API, its database and its backups hold only ciphertext.
  Logs, telemetry, the sync snapshot, MCP and webhooks never carry sealed values; the owner's own
  endpoints don't return them either (the browser can't open them, so it gets field names,
  fingerprints and times). Only the bridge's own device endpoints return them.
- **Not integrity from the cloud.** The public key is public: anyone holding it, the API included,
  can seal a value the bridge will accept. A malicious API could also hand the browser its own key
  instead of the bridge's, and read what the user seals. The defense is the fingerprint: the web
  app shows it beside the bridge, the bridge shows its own (`status`, the local page), and a user
  who compares them detects a substituted key. The web app must say so whenever the key changed
  since the user last sealed to it.
- **A stolen device token** can report a new key. It cannot read values sealed to the real key, but
  if the user then re-enters credentials, they are sealed to the attacker's key and served to the
  token's holder. The same fingerprint check is the defense, and revoking the device ends it. The
  web app should make a key change visible ("this bridge's key changed on …; check the fingerprint
  on the bridge") rather than silently asking for credentials again.
- **Lengths are visible.** The ciphertext is as long as the plaintext. An 8-digit access code looks
  like one. Not padded: the fields are short and their formats are public anyway.

## Fields

| Kind | Fields |
|---|---|
| `bambu` | `access_code` |
| `prusalink` | `password`, `username`, `api_key` |
| `moonraker` | `moonraker_api_key` |
| `octoprint` | `api_key` |
| `sdcp` | none |

These are printlog-bridge's adapters' `app_secrets`, the same names as the interim
`[app_printer <id>]` section. `username` is not secret, but sealing it keeps one mechanism. The API
refuses a field the entry's kind doesn't take, and lists each entry's fields as `secretFields`.

## The API contract

### Check-in (`PUT /api/bridges/me`, the bridge)

New optional fields:

```json
{
  "publicKey": "MFkwEwYHKoZIzj0CAQYIKoZIzj0DAQcDQgAE…",
  "publicKeyFingerprint": "6912dab083628b441666abe23f4b8c81bfea54f84e9e350abccbbfc83f9c8954",
  "credentialIssuesVersion": "3f2b9c0e8d7a4b6c9e1f2a3b4c5d6e7f",
  "credentialIssues": [
    { "entryId": 7, "field": "access_code", "code": "undecryptable" }
  ]
}
```

- `publicKey`: send it on every check-in. Missing or null keeps the stored key. A key that isn't
  exactly the shape above, or a `publicKeyFingerprint` that doesn't match it, is a 400
  `invalid_check_in` and nothing is stored. A different key from the stored one replaces it, makes
  the old values stale and bumps the desired version.
- `credentialIssues`: what the bridge can't use, at most 200, replacing the stored issues of all
  its entries (`[]` clears them; missing or null keeps them). Codes: `missing` (the adapter needs
  this field and has no value it can open; also when the only value was sealed to an old key),
  `undecryptable` (a value is there and does not open, or has an unknown version), and
  `rejected_by_printer` (it opened, and the printer refused it). An entry that isn't on this
  bridge, a field its kind doesn't take, or another code is dropped and named in `rejected`
  (`unknown_printer_entry`, `invalid_secret_field`, `invalid_issue_code`).
- `credentialIssuesVersion`: the desired `version` the issues describe. The issues are applied only
  when it equals the current version, so a report about a value the user has since replaced
  doesn't show against the new one; otherwise they are ignored (the next check-in, after the bridge
  has applied the new list, reports again). Required with `credentialIssues`.
- The response adds `publicKeyFingerprint`: the key the API holds for this bridge (null before the
  first one). If it isn't yours, send `publicKey`.

### The desired list (check-in response and `GET /api/bridges/me/desired`, the bridge)

Each printer gains:

```json
{
  "id": 7,
  "kind": "bambu",
  "secretFields": ["access_code"],
  "secrets": [
    {
      "field": "access_code",
      "sealed": "v1.BGwkGIgeM6HGdLeyLXCmoDHqsvWID9eNcKpvlODVwfyM…",
      "keyFingerprint": "6912dab083628b441666abe23f4b8c81bfea54f84e9e350abccbbfc83f9c8954",
      "updatedAt": "2026-10-27T18:05:00+00:00",
      "stale": false
    }
  ],
  "credentialIssues": []
}
```

Only values sealed to the bridge's current key are listed. Setting, replacing or clearing one
changes `version`. The bridge opens each with `printlog-credential:v1:{bridgeId}:{id}:{field}`;
`bridgeId` is in the check-in response. A value that is absent where the adapter needs one is
`missing`. Values from the interim `[app_printer <id>]` section may stay as a local override.

### Owner endpoints (the web app; `InteractiveUserOnly`)

- `BridgeDto` adds `publicKey`, `publicKeyFingerprint` and `publicKeyChangedAt` (null until the
  bridge sends a key: an older bridge can't take sealed credentials; say "update the bridge").
- `BridgePrinterDto` (in `GET /api/bridges/{id}/printers` and the connect response) adds
  `secretFields`, `secrets` (each `field`, `keyFingerprint`, `updatedAt` and `stale`; **never**
  `sealed`) and `credentialIssues` (`field`, `code`).
- `PUT /api/bridges/{id}/printers/{entryId}/secrets/{field}` with
  `{ "sealed": "v1.…", "keyFingerprint": "<the fingerprint you sealed to>" }` sets or replaces
  one value and returns the entry (200, `BridgePrinterDto`). It clears that field's issue and
  changes the desired version.
- `DELETE /api/bridges/{id}/printers/{entryId}/secrets/{field}` clears one (204, also when there
  was none) and changes the desired version if there was one.
- Errors (problem details with a `code`): 404 for a bridge or entry that isn't yours; 400
  `invalid_secret_field` (not one of the entry's `secretFields`), `invalid_sealed_value` (not the
  shape above: the API checks the prefix, the encoding, the length and that the ephemeral key is
  on the curve, and nothing else), `invalid_key_fingerprint` (not 64 lower-case hex characters);
  409 `bridge_key_missing` (the bridge has reported no key yet) and `bridge_key_changed` (the
  fingerprint isn't the bridge's current one; the problem body carries `keyFingerprint`, the
  current one: fetch the bridge, show the new fingerprint, and seal again).

The web app seals with the `publicKey` from `BridgeDto`, sends the fingerprint it sealed to, and
handles `bridge_key_changed` by reloading the bridge. It never stores the plaintext.
